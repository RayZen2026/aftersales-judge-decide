# 业务背景：升级售后补偿方案 → 判责 SKILL 映射

> **本文件范围**：基于《升级售后补偿方案设计说明.pdf》梳理判责 SKILL 的业务背景，并把业务步骤映射到 SKILL 实现位置（AGENT / AST / 纯数学）。
> **用途**：Phase 1.5-1.7 AGENT prompt 探针的业务依据——探针 prompt 必须覆盖 §4 业务规则。
> **约束**：设计方案已拍板（v1.5 doc，**不大调整**）。本文件只做梳理映射，不引入新设计。

---

## 1. 业务目标

- 水果是非标品，次品与品质波动正常；升级售后 = **规则搞不定、双方谈不拢时，给出一个大家基本能接受的补偿方案**
- 现状痛点：门店觉得赔少了不接受 / 商家物流觉得判错了要申诉——两边都不服 = 方案不够公允、不够清楚
- 目标：把补偿从"凭感觉定、靠人来拍"变成"**按规则算、有依据可查、说清楚为什么**" → 门店留存，责任方不申述
- 旧做法三宗罪：不统一（不同审核员判得不一样）/ 说不清楚 / 顾此失彼

---

## 2. 核心理念：三方利益平衡 = 算总账

| 利益方 | 诉求 | 平台考量 |
|---|---|---|
| 门店 | 赔得越多越好，赔少了就走人 | 门店是资产，流失了要花更大成本拉回 |
| 商家/物流/代理人 | 被扣得越少越好，扣多了要申诉 | 申诉消耗运营精力，伤合作关系 |
| 平台 | 控成本 + 保门店 + 少申诉 | 综合成本最低的平衡点 |

**总代价 = 平台直接掏的钱 + 门店流失的损失 + 商家申诉的成本** → 选总代价最小的方案。
不是"最多"也不是"最少"，而是"**最划算**"。博弈视角：平台先定方案，预判门店/商家反应后取三笔账之和最小。

---

## 3. 业务决策流水线 ↔ SKILL 实现映射

补偿方案是 3 步流水线，每步产出 = 下一步输入：

| 业务步骤 | 业务内容 | 产出 | SKILL 实现位置 | 调 LLM? |
|---|---|---|---|---|
| ① 门店画像 & 风险识别 | 价值/行为/信誉 3 维度 → 高/中/低价值等级 + 薅羊毛风险评分 | 门店价值等级 + 风险标签 | 主流程阶段 2 batch：维度表 JOIN + **门店分层 AST 求值**（门店分层规则表，`store-tier-rules` SKILL import）| ❌ 纯 AST |
| ② 责任怎么分 | 先看证据再定责任；5 类责任方；多方按证据强度分比例 | 责任分配比例 | **AGENT 2 承担方比例判责**（判责规则 AST 仅 prompt 引用，按优先级遍历）+ **分配校正**（纯数学兜底 Σ=100）| ✅ |
| ③ 赔多少最合适 | 三笔账最小化（平台直接成本 + 门店流失损失 + 商家申诉成本）| 赔付金额 + 退货/赔付决策 + 决策依据 | **AGENT 1 门店期望判定**（门店想要什么）+ **AGENT 3 综合判责意见**（最终决策 + 推理链）| ✅ |

> **注意**：AGENT 1 判的是"门店期望"（门店希望怎么判），不是门店画像本身——画像 = 维度数据 + AST 分层，阶段 2 batch 纯计算不调 LLM。
> AGENT 切分当前基线 = 3 AGENT 串行（设计源 doc 8.3 拍板）；**1 vs 3 探针决定是否切 1 AGENT，见 §5**——无论 AGENT 数量如何，业务步骤覆盖不变。

## 4. 业务规则清单（AGENT prompt 必须覆盖 = 探针验证点）

### 4.1 责任判定

| 规则 | 内容 |
|---|---|
| 5 类责任方 | 商家（品质问题/错发少发）/ 物流（配送损坏，**仅自营区域**）/ 代理人（配送/暂存问题，**仅代理人区域**）/ 门店（举证不规范/报损太晚）/ 平台（规则不清/客服超时）|
| 物流/代理人路由 | 按门店区域**互斥**：自营区域归物流，代理人区域归代理人；一个案件两者不同时存在 |
| 多方比例 | 单方问题 = 全责；多方问题按证据强度分比例（证据越充分、问题越严重，比例越高）|
| 平台上限 | 平台最多担 50%（非代理人区域，和商家最多五五分）|
| 代理人门槛 | 代理人只有 2 种情况出钱：① 实质性过失 ② 高价值门店"维护补偿"（上限 ⚠️ 见 §6 待确认）；否则由平台和商家分担 |
| 门店过失 | **不进分配比例**——总赔付金额打折，不体现为"门店承担比例" |
| 说不清楚的案子 | 不硬判 → 推人工复核（对应 5 状态"已处理-需人工" + 9 类失败的 2 业务类）|

### 4.2 赔付决策

| 规则 | 内容 |
|---|---|
| 诉求类型 | A=纯赔钱；B=纯退货（没提金额的按订单金额兜底）；C=退或赔都行（两条路都算，选总代价小的）|
| 退货 vs 赔付 | **二选一互斥**；退货前提 = 剩余货架期 > 0；能退才对比退货/赔钱代价 |
| 退货物流费 | 10 元/次，商家承担 |
| 薅羊毛 | 风险超阈值 → **直接拒赔** + 要求更充分举证（举证门槛筛选真实诉求）|
| 门店流失 | 3 层：平台级（权重 5）/ 品类级（权重 4）/ 商家品类级（权重 1）；**当前阶段只做平台级** |
| 商家申诉风险 | 当前阶段用"商家单笔承担上限 M_cap"控制（扣超部分平台补），不做精细概率模型 |
| 策略旋钮 | λ（门店价值系数，调高=保门店）/ M_cap（商家单笔上限，调高=平台少出钱）——运营按季度策略调 |
| 二次审批 | **和模型解耦**——模型不管审批线，人工审批环节自己判断 |

### 4.3 推理链（决策依据输出要求）

每笔决策输出完整推理链，让审核员/门店/商家都看明白：

1. **门店画像**：什么等级、风险高不高
2. **责任判定**：看到什么证据、哪些责任方、各担多少、为什么这么分
3. **风险评估**：全赔/赔一半/不赔的流失概率；商家不同承担额的申诉概率
4. **最终决策**：算了哪几条路、每条代价多少、选了哪条、为什么

→ 对应 AGENT 输出 schema 的 `reasoning` / `key_factors` / `judgment_summary` 字段（`assets/agent{1,2,3}_prompt_template.j2` 占位版已含，Phase 1.5 探针调优）。

## 5. 1 vs 3 AGENT 探针决策（关键细节，明确成文）

> 设计方案 v1.5 §0.1 / §0.5 / §9 P0，D-20260807-004（确认拍板）。

- **当前基线** = 3 AGENT 串行 + 3 次 LLM 调用（设计源 doc 8.3 拍板，**不是占位**）
- **探针目标** = **1 vs 3 二选一**（不是 1/2/3/5）：**1 AGENT 探针通过 → 改为 1 AGENT；不通过 → 保持 3 AGENT**
- **判定标准**（`assets/eval/eval_standard.md`）：准确率 ≥ 85% / 一致性不一致率 ≤ 5% / latency P95 / 格式校验 100%
- **探针步骤**：Phase 1.5 先跑 1 AGENT 完整流程（5-10 样本）作基线 → 3 AGENT 单 AGENT 探针 → 对比决策（详见 `references/implementation_plan.md` Phase 1 / 1.5）
- **若切 1 AGENT**——影响面锁在 LLM 调用层，设计方案无大调整：

| 变 | 不变 |
|---|---|
| 3 次串行 LLM 调用合并为 1 次（prompt 融合 3 模板职责）| 5 状态机 |
| retry 计数：3 AGENT 独立计数 → 单调用计数 | 9 类失败分类 |
| AGENT 3 独立链失效 → 改用共享 4 模型链（⏳ 探针拍板项）| 抢锁 / stale 5min |
| | 写表规则（任务表 update / 结果表 insert 1 单 1 行）|
| | cron / 飞书通知 / 24h 去重 |
| | 分配校正步骤（纯数学）+ 门店分层 AST（batch）|

- **若保持 3 AGENT**：按现基线进 Phase 2，无需任何调整
